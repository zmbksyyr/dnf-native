# 实施阶段与验收

P0 已完成，用户已授权进入 P1。当前执行证据见[实施记录](06-progress.md)；下表是完整退出要求，尚未通过的项目不因已经开始该阶段而视为完成。每个可审阅步骤检查后提交 Git，记录实际通过项和未通过项。

## 1. 阶段与否决条件

| 阶段 | 交付与进入条件 | 必须通过的退出关卡 | 失败时的处理 |
|---|---|---|---|
| **P0 调研与方案** | 需求原文、纯纪律 AGENTS、静态资源/网络来源、方案与验收计划 | 原文身份、19 项静态清点、证据与脚本一致、文档链接、Git 分阶段提交 | 修正文档或证据；完成后等待用户审阅 |
| **P1 可行性封样** | 用户审阅后，从本项目新代码开始；独立锁定工具链、双架构用户库、官方 MySQL/CRT、插件与测试配置 | 下述 G1–G6 全部成立；原版 manager 至少进入真实业务初始化并得到具体缺口；形成完整候选包预算 | 保留失败现场并复审具体路线；不直接进入大规模 GUI/服务实现 |
| **P2 运行内核与插件** | 沿 P1 已验证路径补齐原程序实际依赖，建立可执行 CLI 和服务清单 | VM/fd/socket/线程/futex/信号/IPC/进程契约通过；原版 DP2/Lua/Frida 双向调用与真实 game 函数通过；未知行为明确失败 | 不用 stub、跳过或降配掩盖缺口 |
| **P3 core 业务链** | 启用默认 16 个原版服务及同版本 DB，按实际依赖编排 | 16 服务真实就绪、互通、原有 DB/日志行为；匹配客户端登录→选角→进图→结算→存档→重启读取；插件与固定地址补丁同时通过 | 逐项定位到原程序、ABI、配置或数据；监听不算通过 |
| **P4 完整模式与资源变体** | 加入原版安全三件套与经证实必要的 TSS/antisvr；封样第二等级组合和 70S2 来源 | 19 项完整验收；core/full 可选性对照；同宿主构建切换 ELF/PVF；补丁与 hook 冲突用例 | 核心链必需组件不得放入“可选”规避；缺失的等级资源不标完成 |
| **P5 产品化** | 将封样数据库引导、控制器、Win32 GUI 和包清单形成完整产品 | MySQL 单文件与普通用户本地依赖；备份/还原/回滚及断电窗口；全部 GUI 操作；最终 core ZIP 实测不超上限 | 功能或体积失败均不发布；不删除必需能力换取达标 |
| **P6 三系统离线验收** | 从同一候选发布包开始，独立的 Win7/10/11 x64 原生环境 | 下述系统矩阵、业务矩阵、来源审计全部通过；长期工作负载及重启测试留证 | 任一目标系统失败即不宣称三系统完成 |

P1 的数据、依赖闭包和尺寸实验是早期可行性样件，不能替代 P5 的产品实现与故障恢复验证。阶段可以因实际依赖细化为多个小提交；没有依据时不承诺日期或工期。

## 2. P1 的六个硬关卡

| 编号 | 必须得到的证据 | 不算通过的结果 |
|---|---|---|
| G1 原址与 VM | 两架构真实映射、guest ELF/ld 启动栈；Win7 固定地址及 4 KiB/64 KiB 场景，文件偏移/COW/共享双别名/部分解除映射 | 仅解析 ELF、私有内存拷贝、只在 Win11 新 API 下通过 |
| G2 syscall / TLS | 两架构真实入口，调度压力、多模块 TLS、动态加载、外来回调、寄存器与信号/异常重入，适配记录可审查 | 只设一次 FS/GS、仅线性扫描、只验证单线程 hello |
| G3 插件与地址共存 | 原版 DP2 保护库初始化、Lua→JS→game 与反向回调、hook/补丁/必要适配同时执行 | 换空插件、只加载 DLL、只写一条日志 |
| G4 x64 原版 STUN | 固定哈希 `df_stun_r` 进入真实路径并完成原协议 UDP 往返 | 重编 x86 STUN、仅绑定端口、测试模块替代 |
| G5 数据与免安装 DB | 官方包身份、同版本物理恢复→逻辑种子→新实例；干净目标系统上的本地 CRT/UCRT 及四工具工作 | 借用其他项目现成数据库、开发机已安装运行库、只初始化空库 |
| G6 包体与来源 | 包含完整候选依赖的代表性 ZIP；精确字节数、来源白名单、必需/可选分类证据 | raw DEFLATE 估算、遗漏系统库/PVF、引用历史小包尺寸 |

G3 在原版 game 初始化之前可能暴露新的 syscall/动态代码需求，可在 P1 小步补齐必要子集；达到该关卡前不开展大量周边 API 仿制。若不得不引入用户排除的模拟器/驱动、改变 game 地址或牺牲原脚本兼容，必须判定候选路线失败。

## 5. 数据库故障注入清单

在可丢弃的测试实例执行，原包始终只读：

- 初始化中止、并发首启、payload 缺失/篡改和错误实例身份。
- 全表锁持有失败、导出中止、备份介质写满和归档哈希错误。
- 预快照复制失败、缺少空间、还原 SQL 中途失败或版本不匹配。
- 影子验证失败、指针切换前/后进程被终止、控制器重启恢复。
- 新库启动失败、服务业务检查失败、正常回滚及回滚本身失败。

每项必须核对旧数据是否仍可恢复、活动代次是否唯一且明确、UI 是否报告真实状态；不能只检查操作函数返回值。

## 6. 证据格式与 Git 纪律

每个能力记录以下字段：阶段/关卡、UTC 时间、自研提交与构建哈希、OS 构建/权限/网络状态、原 ELF/DSO/脚本/PVF 哈希、用户库与 MySQL/CRT 版本、配置摘要、实际可用的复现命令、退出码、日志/协议/数据证据、结果与已知缺口。秘密值不得写入记录。

结果使用“未运行 / 失败 / 静态通过 / 原语通过 / 接口通过 / 业务通过”等明确等级；参考实验单独标“参考，不是交付”。样件与自编测试 ELF 可以验证原语，不能计入 19 个原版服务的业务验收。缓存和大日志放在忽略目录，以摘要与哈希关联必要证据。

每阶段先更新方案与实际记录，检查后提交；超出已批准路线的重大变更形成独立决策记录。不得用后续提交标题覆盖早先失败、把多个未验证子阶段合称完成，或借其他项目的测试输出补本项目证据。
