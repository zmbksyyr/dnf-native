# 客户端对照与本地地址配置

## 本轮实际问题与修复

已授权的 jbz69 客户端在独立副本中加载到频道选择界面，显示 `ch.11` 和连接等待提示。此次客户端与服务端同时使用原包的未修改 PVF，只作为资源一致性对照，不是当前 jbz69 定制 PVF 的验收。

实际 channel 日志仍将游戏地址发布为 `Public IP:10011`。独立实例的 `game/cfg/siroco11.cfg`、备用 `siroco56.cfg` 和 `auction/cfg/bridge.cfg` 残留原包的 `Public IP` / `UDP IP` 占位符；原有准备脚本只替换数字 IP，遗漏这些文字。这是已确认的本地配置生成问题。

按当前单机支持场景，将这些占位符替换为 `127.0.0.1`。开发准备脚本在复制配置时处理；原生 GUI 在资源复制/解压及原始哈希核对完成后处理，因此现有 CAB 也可用，无需修改输入包或重制大资源包。该行为只在新建实例时执行，不自动改写已有实例或引入公网配置功能。

本轮已有独立测试实例在 game 正常退出后备份并修正配置。单独重启时，原版 monitor 拒绝重复注册的频道 11，game 正常退出；随后正常停止并重启整组测试服务，monitor 重新接受登记，channel 实际日志出现：

```text
Add SGI=4, IP= 127.0.0.1, PORT= 10011, gc_no=3011
```

这证明服务端发布地址已修正，尚未证明客户端认证或角色登录通过。验证身份只在私有复制数据库中新建，账号、口令、RSA 私钥和登录票据不提交 Git。

## 当前 jbz69 PVF 的进一步核对

只读解析依据原版 ELF 的 PVF 解密循环及索引读取行为，核对解密目录和提取文件的 CRC。当前定制 PVF 有 439165 个索引项、94583 个 `.equ` 文件；其中 54 个文件包含 `equipment/character/atswordman.lay` 的字符串表引用，但归档中没有该文件。主要位于 `swordman/at_avatar`，不能只检查 `atswordman/` 目录。

原包可启动 PVF 同样只登记十个动画模板，也没有这个 `.lay`；“缺少该文件”本身不是全部结论。当前定制数据确实请求了缺失模板，并与此前原版 map 查找失败后继续解引用的现场相对应，详见[启动故障](08-compatibility-and-performance.md)。没有添加假模板、删除物品或跳过原版解析。

现有四份备份 PVF 的字符串表也含三个缺失模板名；本轮没有逐份证明这些字符串都被实际物品引用，也没有逐份启动，不能宣布四份全部不可用。当前对照采用原包 PVF，双方 SHA-256 为 `c3dde22a8b19e5deff5c498533e0830d13fec5605e81adeda9373841e6e22dec`；用户所指当前定制 PVF 的 SHA-256 为 `dc444c3429a44c19419dba83c8b1c30e4263371afa528ba90430fda2f598e1e2`。两条结果分别记录。

## 验证范围

配置生成回归复用真实首次创建专项，使用已有 CAB 和重新构建的 GUI，检查三份配置中的占位符已消除，同时保留原有资源身份、数据库往返和原版 peer 协议检查。具体版本、结果与审阅包哈希见[本轮证据](evidence/p9-local-addresses.json)。

Windows 10 开发机上的客户端确已进入频道界面；后续桌面截图 BitBlt 返回错误 6，前台窗口获取为空，输入助手在前台检查失败时没有发送点击。没有把桌面操作受阻、进程存活或服务端启动当成登录、进图、存档通过。原版 game ELF 和输入客户端保持不变，客户端仅使用独立副本。
