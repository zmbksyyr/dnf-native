# 数据库、GUI 与离线交付方案

本文件是[运行方案](02-technical-plan.md)的配套设计。数据库固定为官方 Windows x64 MySQL 5.7.44；GUI 在本项目内用 Win32/C++ 从零实现。官方文件导入和原始数据逻辑往返已有本机可复现实验；独立单文件引导首版已完成本机实测，GUI 和最终交付仍未完成。

## 1. MySQL 单文件发布

`mysql-standalone.exe` 是本项目独立编写的引导程序，内部封装官方 5.7.44 payload，最终最小依赖闭包仍待裁剪和验证。解压后执行真实官方 `mysqld/mysql/mysqladmin/mysqldump`。源码、四个 PE、DLL、字符集、必要 share/plugin 文件和分发材料分别锁定来源与哈希。

当前单文件约 16 MB，精确大小与哈希记录在构建和阶段证据中。使用系统 Cabinet FDI 解压内嵌 LZX CAB，CNG 校验文件哈希，以 Win32 CreateProcessW 调用四个官方工具。`prepare INSTANCE` 解压到实例内 `.mysql/payload-<manifest hash>`；`mysqld|mysql|mysqladmin|mysqldump INSTANCE [官方参数]` 执行工具并转交标准输入输出与退出码，mysqld 的 basedir/datadir 固定在该实例内。并发准备使用文件锁，展开后校验再提交目录；已有缓存逐文件校验，失败明确返回错误，不覆盖数据库。

官方 5.7 客户端的 defaults loader 在本机不能读取中文绝对配置路径。子进程工作目录固定为实例目录，控制器使用 `--defaults-file=client.private.cnf` 这类固定相对文件名；该方式已在中文/空格/括号实例目录中完成 TLS 读写和备份还原。8.3 路径仍可能含中文，不能依赖它解决此问题。首版保留整个官方 share 目录，尚未做最终按访问记录裁剪。

复现命令为 `python tools/import_mysql_runtime.py`、`python tools/build_mysql_standalone.py`、`python tools/test_mysql_standalone.py`。首版测试只在开发机 Windows 10 完成，包含四工具版本、四进程并发准备、私有新库初始化、TLS、两行二进制数据备份/还原、已有库拒绝重新初始化、修改缓存拒绝运行与正常停服。VC++ 三个 DLL 的实际加载位置为实例缓存；Windows 10 的 UCRT 仍由系统提供，Win7 本地 UCRT 尚未实测。首版证据见 [单文件引导](evidence/p4-mysql-standalone.json)。

`initialize INSTANCE [PORT]` 已实现原生安全首次初始化：只接受没有 data 和数据库配置的新实例，使用官方 `--initialize`；经 `--skip-networking` 的随机命名管道，以官方临时密码设置 CNG 生成的 48 位十六进制密码，验证新凭据，再正常停库。写出的 `server.cnf` 固定本机地址、所选端口、lower_case_table_names=1 和 latin1；`client.private.cnf` 强制 TCP/TLS。data、配置与私有日志使用受保护 DACL，只允许当前 Windows 用户，data 的规则可继承到子文件。密码通过标准输入传 SQL，不进入命令行或普通输出。失败保留私有数据与诊断，不重新初始化既有实例。

安全版本在中文实例中实际完成初始化、重启、TLS、备份还原及正常关闭；预定 TCP 端口被独占时初始化仍成功，空密码 root 被认证拒绝，敏感目录/文件的实际 DACL 通过检查。已有实例重试不改变 data 中任何文件。证据见 [安全初始化](evidence/p4-mysql-secure-initialize.json)。GUI 密码设置、跨 Windows 用户迁移、备份/回滚控制流程仍待实现。

后续复测发现命名管道停服时，mysqladmin 和 SQL SHUTDOWN 都可能丢失关闭确认。引导使用 SQL SHUTDOWN，并独立等待自有服务器；仅在服务器返回 0、日志出现 Shutdown complete、客户端错误明确为 ERROR 2013 时，将其记录为确认丢失并提示。其他客户端错误、服务器错误和超时仍失败。客户端非零结果保持原值，未改写为 0。证据见 [原始数据实测](evidence/p4-mysql-original-seed.json)及[服务链接入](evidence/p4-mysql-core-integration.json)。

原版服务配置及 d_taiwan.db_connect.db_passwd 保存 24 字节 XTEA/ECB 密文的十六进制形式，不能填管理员配置里的明文密码。已根据原版 DBMW 的构造、解码和分组函数核实格式，独立实现 tools/legacy_db_password.py；固定材料只从哈希锁定的原版 ELF 读取，材料和真实口令不进 Git。隔离测试账号采用 16 个 ASCII 字符，经该格式编码后，三路 DBMW 和 auction/point 均完成真实连接；管理员配置继续使用独立的强随机凭据。GUI 密码配置仍待接入这一约束。

不得把“只携带四个 EXE”视为完整闭包。静态普通/延迟导入、运行期 DLL/插件/数据文件访问、中文路径、初始化、查询、备份、还原及 TLS 连接都参与闭包判定。VC++ 2019/UCRT 采用可分发且经 Win7/10/11 验证的本地部署组合，不能要求另装 VC Redist，也不能直接从开发机 System32 抄取 DLL。开发工具使用何种 CRT 不改变这一产品要求。

建议支持内部操作：查询版本、准备 payload、初始化空实例、启动/停止、mysql 客户端、备份与还原。具体命令行协议在实施阶段定义；GUI 和控制器使用受控操作接口，密码不出现在命令行或普通日志中。

首次运行流程：

1. 校验自身 payload 目录、清单和哈希，获取实例准备锁。
2. 解压到实例下的新临时目录；拒绝路径穿越、越界链接和重复路径，限制展开大小。
3. 校验全部展开文件和版本，成功后原子提交到按 payload 哈希命名的缓存；并发首启只产生一份有效缓存。
4. 仅对全新空数据目录执行 `mysqld --initialize`，在临时受控凭据流程中设置实例密码；初始化失败保留诊断，不触碰既有目录。
5. 启动前检查实例身份、数据目录、配置和端口占用；使用显式绝对路径与安全的 Windows 参数编码创建进程。默认绑定本机。
6. 验证 `SELECT VERSION()`、server UUID、目标库/表和基本读写，才报告数据库就绪；不以进程存在或端口可连代替。

已有数据目录禁止重新初始化。可写状态全部放在实例目录，不能写入只读安装目录；解压目录必须可由当前普通用户写入。没有管理员权限、Windows 服务注册、系统 PATH 修改、联网安装或隐藏自动升级。

## 2. 原始数据恢复与逻辑种子

资源调研已确认输入为物理数据库。恢复过程与新实例初始化严格分开：

- 从只读原包生成独立恢复工作副本，记录所有源文件哈希、MySQL 版本和恢复参数。
- 分析 `.frm`、MyISAM 配套文件、`ibdata1`、原配置与安装器自解压内容，核实引擎、字符集、排序规则、时区、SQL mode、触发器、事件、账号/权限和通道配置。本轮未执行安装器。
- 在同版本 Windows MySQL 下验证受控恢复。不能通过删除未知数据文件、覆盖原库或采用未验证的强制恢复级别宣称成功。
- 若能完整读取，导出可复现的应用逻辑种子及必要权限/配置；导入全新实例，核对结构、关键行、关联关系和服务实际查询。
- 未能恢复时保留失败证据，列出缺失的完整备份或逻辑种子。不得混入 `opendnf` 的现成数据、不同等级 PVF 或其他 MySQL 版本来冒充原包恢复。

`lower_case_table_names=1` 在初始化前确定，记录为 Windows/NTFS 偏差。先检查库、表、触发器及 SQL 标识符冲突，再迁移；不能只改文件名。源代码中使用的编码及旧认证行为需通过真实客户端/服务路径确定，不全局放宽 SQL mode、关闭校验或统一改成另一个字符集。

数据资源不进 Git；逻辑种子作为封样发布资产独立记录来源与哈希。未来由本项目编写的迁移代码可以版本化，真实玩家数据、密码、物理数据目录和用户备份始终排除。

## 3. 停服逻辑备份

“停服”指停止所有 DNF 写入进程并确认存档完成，MySQL 维持运行以便逻辑导出。默认流程是：锁定实例操作 → 检查磁盘空间 → 有序停服 → 确认写入者退出 → 一致性导出 → 校验归档 → 按操作前状态恢复运行。

原包存在 MyISAM，不能用 `--single-transaction` 单独证明所有表一致。选择经验证的全表锁导出或持有全局读锁的会话；锁必须覆盖实际导出周期，不能运行一条随后退出的 mysql 命令就认为锁仍有效。导出包括应用表、触发器、存储过程、事件及所需账号/权限元数据，具体选项依据引擎和字符集封样。

备份先写临时文件，检查子进程退出码、stderr、文件完整性和哈希，再原子命名。清单记录实例/版本、数据库集合、结构摘要、关键行数、时间、编码与校验信息；首次交付和后续抽样需在临时实例真实还原，不能把“文件非空”视为可恢复。

Windows 5.7.44 的完整备份捕获 mysqldump 标准输出到宿主以二进制方式打开的文件，导入使用 mysql 标准输入与 --comments --binary-mode。不能直接以 --result-file 的输出替代这条路径：官方 client/readline.cc 的 Windows 分支无条件删除每行 LF 前的一字节 CR，--binary-mode 不改变该分支。mysqldump 的文本标准输出会补入对应 CR，实际往返可保留原有存储程序换行；--result-file 绕过这一步，原始数据实测丢失 1056 个 CR。已用原始 18 库、601 张表做完整导出、删库、还原、再导出，三份种子/备份/再导出的 977716 字节及 SHA-256 完全一致，未归一化或忽略差异。两行二进制样本的 result-file 测试仅覆盖其原有范围，不能替代这项完整实测。

失败时保留旧实例和诊断，明确是否已恢复服务。只有服务再通过就绪检查后才显示恢复运行成功。凭据通过访问权限受控的临时配置或进程接口传递；不在命令行、备份明文元数据或日志中回显。

## 4. 预快照、还原与回滚

当前原生维护采用固定 `data/`、还原副本和持久切换标记，直接复用已有实例布局：

```text
INSTANCE/
  data/                       活动数据目录
  restore.pending             未提交的还原操作名
  .mysql/restore-<id>/
    before.sql                切换前的完整逻辑预备份
    shadow/data/              逐文件复制并核验后的还原副本
    restored.sql              副本还原后重新导出的验证结果
    previous-data/            切换时保留下来的原始冷数据
    import/、verify/、active/   各阶段独立的私有日志
```

`backup INSTANCE NEW_DIRECTORY` 只接受已停止实例，在实例外创建当前用户独享的新目录；用官方共享内存协议和 `--skip-networking` 启动自有 MySQL，导出应用库、MySQL 账号和存储对象，正常停库后写入清单。清单保存 UUID、连接配置哈希和 SQL 哈希。完整导出排除可再生的 `mysql.innodb_index_stats/innodb_table_stats`，以及已由 `--routines/--events` 导出定义的 `mysql.proc/event`；不重复保存其随重建变化的内部时间戳，不对结果做归一化。命名管道在本机对 262144/811848 字节 SQL 已复现 ERROR 2006，官方共享内存协议对应请求通过，因此维护批量 SQL 使用该协议。初始化的小 SQL 继续保留原有命名管道路径。

`restore INSTANCE DIRECTORY` 的当前流程：

1. **检查**：验证格式、SQL 哈希、UUID 和连接配置。备份输入在整个导入期间禁止其他写入；实例操作锁禁止启动、初始化和维护并发，另检查 InnoDB 文件已释放。当前仅支持同实例、连接配置未改变的还原。
2. **预备份与冷副本**：启动自有维护库保存 `before.sql` 后正常停止。原 `data/` 保持完整，逐文件复制到 `shadow/data/`，刷新并比较每个文件的 SHA-256；失败不进入切换。
3. **副本导入**：仅在副本中删除当前应用库，再导入选定备份，包括系统账号；重新启动使系统账号生效。官方客户端通过相对配置文件名工作，避免已复现的中文绝对配置路径问题。
4. **逐字节验证**：副本重新导出为 `restored.sql`，要求与备份 SQL 的 SHA-256 完全一致，再正常停止；任何差异均保留活动库。
5. **切换与提交**：先持久化 `restore.pending`，再将原 `data/` 改名为操作内 `previous-data/`，将已验证的副本改名为 `data/`。启动后用真实 SQL 核对 UUID 和凭据，再正常停止并删除未提交标记。保留旧冷数据、逻辑预备份和验证日志。
6. **失败回滚**：切换发生异常时自动恢复 `previous-data/`。若有未提交标记，常规启动被拒绝；`recover INSTANCE` 按实际目录状态保留失败数据并恢复原冷库，结果保持停库，随后由控制器决定恢复哪些 DNF 服务。回滚失败则保留标记和现场，明确报错。

两个目录改名不是一个原子操作，因此切换标记先落盘，自有官方子进程在执行前被加入带 KILL_ON_JOB_CLOSE 的 Windows Job。包装进程被终止时其子进程同时结束，下一次维护必须先恢复未提交操作。启动前、两个改名之间和激活后三个窗口分别验证恢复；实际的 Windows 目录共享冲突用于验证原库已移走后的自动回滚。构造窗口状态不等于断电实测。

一键协调 DNF 停服、维护及恢复运行，空间预估、磁盘写满与断电故障、密码迁移及跨实例还原仍待完成。当前原生操作直接拥有其维护进程和本机通信端点，不根据端口或外部 PID 停止其他 MySQL；恢复操作限定在实例内由本项目创建的还原目录，不自动删除旧冷数据。

## 5. 自研 Win32 GUI

GUI 使用 Win32 控件与 C++ 消息循环，调用实例控制器，不加载参考 `Launcher.cs`、参考 EXE 或历史 GUI。耗时操作在工作线程/子进程执行，以操作 ID 和异步事件更新界面；窗口不能因备份或停服阻塞。

首版 `DNF-Native.exe` 已实现实例选择、端口输入、安全初始化、数据库启停、备份、还原、未完成还原恢复和日志目录入口。所有动作调用相邻的本项目 `mysql-standalone.exe`，不依赖 Python、.NET 或参考 GUI；Win32 公共文件权限/参数转义函数因两个实际调用方提取到 `win32_files.h`。SQL 就绪检查同时核对版本、实例 UUID、本次创建的 pid 文件名与 TLS；关闭窗口正常停止其自有数据库，不根据端口停止其他实例。数据库运行或操作未结束时禁止维护切换。

真实窗口测试已覆盖中文路径、初始化、备份和还原期间消息响应、另一 UUID 占用相同端口时失败且原库继续可用、二进制行还原、新增库清除、损坏备份报错、关闭窗口正常停库，以及磁盘上未完成改名状态的恢复按钮。证据见 [Win32 数据库界面](evidence/p6-win32-gui.json)。服务界面接入见下文；日志筛选/脱敏导出、密码编辑、插件与等级配置仍未实现。仅开发机 Windows 10 实测，不能据此声明完整 GUI 或多系统验收完成。

服务编排实现使用实例自己的 `services.ini`：它只保存原版服务的相对路径、ELF/解释器哈希、参数、环境和停止信号，不保存数据库密码。原生 GUI 读取清单，分别启动两个架构的本项目宿主，展示 19 项进程状态、PID 和原始退出码，提供单项/整体启停及所选服务日志。清单中的默认启动项为 16 个 core；三件安全组件为可选，完整拓扑仍待验证。运行状态明确标注业务未验证，不由监听或进程存活推断业务就绪。

整体启动先取得数据库 SQL 身份，再依清单发起服务进程；整体停止逆序请求原版信号，等待全部自有服务退出后才停库。备份和还原也沿用同一逆序停服路径：实例运行时按钮仍可用，控制器先停止自有服务和数据库，再执行离线维护；若服务不是由当前窗口持有数据库，则明确拒绝操作。某个服务停止超时则保留剩余依赖和数据库供诊断，启动中失败也保留已启动的自有进程。原版前台 CApplication 正常退出后会留下 PID 文件；仅当自有进程已退出、文件内容仍匹配该 PID 时清理。返回码继续原样显示，部分原版前台服务完成清理后本来就返回 1。

GUI 已实现从相邻 `resources/` 创建游戏实例：先校验资源清单与逻辑种子，要求目标目录为空，复制服务与用户库，再通过单文件安全初始化数据库。使用已验证的 977716 字节应用种子导入原始 18 库/601 表，重新导出必须与种子 SHA-256 相同，随后才设置本实例的账号和配置。账号分为维护 root、应用库范围的 game、只读频道库的 bridge、原版脚本需要的 Frida；四种口令分别随机生成，原版配置编码从哈希锁定的原版 DBMW ELF 读取材料并由本项目独立实现。按数据库当前月份从原表创建四张拍卖历史表，未修改种子或原始输入。游戏实例使用原版 bridge 要求的数据库端口 3306。

复制、导入或配置失败会保留 `instance.pending` 和私有日志，界面禁止启动未完成实例；不覆盖现有内容，也不自动删除失败数据。成功后正常停库，最后写入 `services.ini` 并移除未完成标记，默认仍为 core 16 服务。没有相邻资源清单时保留数据库独立初始化入口。资源构建时保留原版 channel/relay 容量，开发探测使用的 16 连接配置不会成为产品模板。

```powershell
python tools/build_service_resources.py --output build/gui-setup/resources --seed PRIVATE_APPLICATION.sql --seed-sha256 d4a3b2021194448730575f50595d7597e38f9b6ff8aaeab080208ef8e84f5198
python tools/test_gui_setup.py
build/gui-setup/DNF-Native.exe
```

`build_service_resources.py` 仅在开发构建时使用。运行时只需同目录的 `DNF-Native.exe`、`mysql-standalone.exe`、`resources/`，通过“创建实例”完成准备，无需 Python 或其他工程目录。本阶段未裁剪资源共 1308 个文件、667534605 字节，包含可选安全资源；不是满足 core/full 分包及 ≤210 MB 要求的最终 ZIP。证据见 [GUI 首次创建](evidence/p6-gui-instance-setup.json)。

开发诊断仍可用 `tools/prepare_service_instance.py` 从原版输入、固定用户库和已停止的安全种子复制新实例；它拒绝覆盖已有目录，并检查源数据库未变。实例布局为数据库的 `data/`、两个配置文件，与 `services.ini`、`hosts/{i686,x86_64}/`、两个架构资源根和 `service-logs/` 并列。没有把参考工程的配置或程序接入此路径。

`--peers-only` 仅用于省去 game 长时间加载的诊断，保留全部 19 项；它不代表产品默认配置。原版服务宿主在执行前加入 GUI 的 Windows Job，正常关闭窗口仍逐项正常停服。MySQL 包装器继续使用自己的 Job，GUI 没有给它再套一层；GUI 被强制终止后的数据库重新接管尚未实现，不能把本机正常关闭测试外推为全部崩溃恢复能力。

插件设置已接入同一 Win32 窗口，提供“启用 DP2/Lua”“启用 Frida”和保存按钮。设置保存在现有 `services.ini` 的 `[plugins] mode=off/lua/frida`，不增加运行配置框架。未设置 mode 的已有实例沿用原有环境；保存后只更新 game 的下次启动环境，不丢弃其他服务的进程句柄。game 运行时禁止修改，停止或退出后恢复编辑；关闭 DP2 会同时关闭 Frida，Lua-only 模式继续加载 DP2 和 Lua。

DP2 关闭通过移除其预加载项实现。Frida 关闭在实例自己的 `df.frida.load` 入口加入环境开关，先保存 `frida.lua.before-native-switch`，再替换实例文件；源资源与用户入口脚本不修改。关闭时记录明确日志并返回原模块文档定义的加载失败值 -1000，不调用 Gadget，默认 Lua 脚本继续执行；启用后仍执行原有加载、hook 与双向调用路径。自定义代码绕过该模块自行加载其他插件不由此设置管理。

70S2 的具体资源、ELF/PVF 匹配和差异包尚未找到并封样；不能宣称已经可用。如果另一等级确需不同 PVF，作为显式版本资源单独处理，不能把不匹配文件与默认 PVF 拼成“无重复”结果。
