# 兼容缺口与运行开销

本轮只读查阅用户指定的 `dnf-winport/rednf` 逆向源码。扫描范围为 DNFServer、ChannelOld、secsvr 的 source 与 tss_sdk，共 22597 个源文件；[来源索引](evidence/p7-reference-api-audit.json)记录候选调用的路径、行号与文件哈希，不包含参考实现代码。词法扫描包含声明、注释和重复文件，源码里出现调用只说明需要核查，是否影响当前服务须再核对原版 ELF 和实际运行；没有把参考工程加入构建或启动链。

可用 `python tools/audit_compatibility.py --reference ../dnf-winport/src_dnf-winport_20261111/dnf-winport/rednf --output build/reference-api-audit.json` 复核索引。已扫描的候选 API 中有 26 种出现匹配；这个数量不表示兼容覆盖率。

## 已明确的兼容边界

| 路径 | 本项目目前支持 | 剩余缺口及影响 |
|---|---|---|
| 原版后台启动 | GUI 使用原版 `run`、`nofork`、STUN `test` 前台入口，Win32 管理进程 | `fork`、`setsid`、进程型 clone 和后台派生未实现。参考普通服务及安全组件存在这些路径；不能把前台启动计为后台语义通过 |
| 安全组件与 TSS | `/dev/shm` 文件命名空间、真实共享文件视图、`msync` 写回已有原语检查 | 参考安全源码还含 SysV `shmget/shmat/shmctl`、`semget/semop/semctl`。这些与 POSIX 文件映射不同，runtime 尚未实现；需要原版完整拓扑触发，不能据候选符号提前宣布必需或可删 |
| socket 与 epoll | 当前 TCP/UDP、channel/relay/STUN 和真实 monitor 拒绝行为通过 | 文件与 socket 共用 256 项描述符表，低于原配置的数千连接容量；需要在扩大负载前补齐。没有完整 `sendmsg/recvmsg` 辅助数据、Unix socket 或全部 epoll 标志语义。安全源码含消息向量调用，客户端负载与大连接数仍待验证 |
| 线程生命周期 | 原版 pthread 创建、TLS、futex 等当前路径已运行 | clone 只接受已观察的 pthread 标志；64 个线程槽及退出后的句柄/槽复用尚需完善。robust owner death、pthread cancel 和通用定向线程信号没有完整支持 |
| 信号与停服 | 当前 SIGTERM、SIGUSR2 和简单处理器返回有实际服务记录 | `SA_SIGINFO`、备用信号栈、异步抢占正在纯计算的线程、完整 syscall 中断/重启语义未覆盖。初始化期间请求停服可能需要等应用走到后续系统调用 |
| 文件行为 | 实际文件读写、锁、目录枚举、关闭目标的 rename、ELF 快照、部分文件共享映射已测 | 已打开目标上的 POSIX rename 替换、符号链接语义、任意私有文件映射及跨多个预留区的固定映射仍有限制；`mremap` 只覆盖已实现的 x86 匿名区移动路径 |
| 文件监控 | Frida 当前已观察到 fallback 后继续运行 | i386 `inotify_init/init1`（291/332）仍返回 ENOSYS；不代表实时脚本/文件监控能力已提供 |
| 资源限制与系统信息 | 当前栈/文件数/禁用 core 等已记录值 | 不是完整 Linux rlimit、procfs 或调度接口；不能承诺原版请求扩大限额、产生 core 或所有诊断工具都可用 |

优先级由真实路径决定：本轮先解决已复现的 game 关闭 DP2 后启动失败和初始化开销，后续推进已获授权的 jbz69 客户端与配套 PVF 的登录、进图及存档；大连接数与安全完整拓扑另做实际验证。尚未触发且不在当前场景中的候选 API 不批量补桩，也不默认返回成功。

## 内存占用的来源

同一轮实际进程观察中，bridge/channel 的私有提交约 1388/1346 MiB，工作集约 1336/1303 MiB；各有一个 1310818304 字节的大匿名区。参考 `ChannelServiceApp.h` 显示固定 1000 个 TCPUser，每个包含两个 655360 字节环形缓冲区，构造时清零。这解释了约 1.31 GB 的主要分配，容量不是简单的 `max_client` 配置就能全部改变。

DBMW/manager 的私有提交也可能远大于工作集：两者分别表示已承诺的私有内存与实际驻留页，不能混用。优化不通过裁掉固定连接池、减小默认容量、强行整理工作集或修改原始 ELF 来制造表面降幅。先修复兼容层已证实的映射泄漏，再评估额外快照复制等自身开销。

## CPU 热点与处理

在实际 game 初始化主线程上取 120 个短暂停顿样本，原先绝大多数落在 Windows 异常派发、TLS 适配与单线程指令缓冲区。原版指令确实在 CPU 上运行，但反复陷入 VEH、解码和重新编码常见 TLS 读指令成本很高。

本项目增加 x86 常见的 GS 绝对地址读取（MOV/XOR/CMP）直接执行路径：由 Windows 线程自己的 TLS 槽取当前 guest TLS 基址，执行同义 CPU 指令，保留其他寄存器、MOV 标志和 CMP/XOR 的结果。仅改装已核对的加载副本，原地址和后续指令位置保留；较短或其他 TLS 指令继续走现有路径。使用 SDK 的 TEB 布局，线程接入时核对槽值；初始 TLS 未设置仍明确退出 126。代码页随对应 ELF 回收。

扩大后的同一 TLS 夹具，x86 旧宿主三次为 4.119–4.169 秒，新实现为 0.257–0.272 秒，中位数约快 15.7 倍；包含 200000 轮读取/比较、寄存器与标志检查、切换 TLS 基址。另有真实并发 guest 线程检查各自 TLS。该时间是本机原语结果，不能写成整服 CPU 降幅。

进一步采样发现 libc 的三字节寄存器相对 GS 读取仍频繁触发异常。CentOS 7.9 glibc 2.17 原包已经提供 `i686/nosegneg` 变体，其同版本实现使用可直接适配的绝对 GS 基址读取；独立对照选择该已随包用户库，没有重建或替换原版 DNF ELF。新建实例的 game 在原有 `LD_LIBRARY_PATH` 前加入该路径；已有实例需显式更新配置和宿主，不会被构建工具就地修改。

首次对照约 34 秒走到游戏世界/密钥初始化后耗尽映射表。此时 1024 条记录均仍有效，约 1.09 GB 映射全部为存活页面，没有残留空记录；这是修复部分 unmap 回收后另一个真实容量不足。映射表增加至 4096，双架构检查 1500 个同时存活的区域及读写、完整释放。宿主状态改用静态存储，避免放大主线程栈。

修复后 GUI 的完整插件专项通过：关闭 DP2 的 game 自然启动约 37.062 秒，观察到原版启动及完整停服标记；正常退出 0，无强制回收。Lua-only、启用 Frida 后的真实 hook/双向 RPC、反复开关、设置持久化、其他 peer 保留，以及 DP2 关闭时的 channel/relay/monitor/STUN 对照均通过。该自然启动耗时只代表本次配置，未与旧宿主在同条件下完成整服时间对照。

## 原版 game 完整运行对照

为分离 ELF 输入存储的收益，构建一个隔离对照宿主，仅将当前只读文件视图改回先前的堆复制；TLS 路径、4096 映射槽和其他源码保持相同。每组均从同一已停止私有实例复制资源与数据库，独立启动 15 个 peer，运行相同原版 game、PVF 和 nosegneg 库。前一轮连续复用 peer 时第二个 game 收到停服请求，未作为稳态成功结果；以下三组均重新创建冷实例并正常完成。

| 观察项 | 堆复制，DP2 关闭 | 文件视图，DP2 关闭 | 文件视图，DP2/Frida 开启 |
|---|---:|---:|---:|
| 自然启动秒数 | 35.859 | 39.383 | 41.133 |
| 启动后闲置 10 秒的私有提交 MiB | 1410.56 | 1341.15 | 1493.93 |
| 同时工作集 MiB | 728.86 | 728.996 | 871.91 |
| 闲置 10 秒使用的 CPU 秒 | 0.03125 | 0.046875 | 0.0625 |
| 正常退出码 | 0 | 0 | 0 |

DP2 关闭的同条件对照减少约 **69.4 MiB 私有提交**，工作集相近；这不等于物理内存释放同样大小。三组耗时为单次本机观察，不据此声称文件视图提升初始化速度。开启插件时额外映射与分配属于另一种运行配置，不能与关闭插件的结果合并计算优化降幅。两组文件视图运行的闲置 CPU 分别约占单核心 0.47% 和 0.63%；每组 15 个 peer 合计在独立 10 秒窗口消耗约 0.31–0.45 CPU 秒，主要为 bridge。

每组均通过 channel 拆包/连包、relay 双向转发、真实 monitor 拒绝未登录账号及 STUN 原语。开启插件的完整运行保留原版 Lua/Frida，完整停服包含 Gadget dispose 和 DP2 unload；仅观察到已知 inotify fallback。源冷数据库在各组前后保持相同。没有登录玩家的闲置结果不能外推到客户端负载。

构建哈希、三个独立 receipt、原语检查及失败对照边界见[本阶段证据](evidence/p7-runtime-performance.json)。

所有观察限本机 Windows 10 10.0.19044。原版固定缓冲池、Windows 提交模型、DP2 开关带来的分配器差异与真实客户端负载需要分别测量。

## jbz69 当前 PVF 的实际启动阻塞

按用户授权，复制 jbz69 客户端并将其当前 237024513 字节 `Script.pvf` 装入独立服务实例。原版 game 成功连接数据库并加载地下城等资源，在物品初始化期间反复崩溃，尚未启动客户端，不计登录或业务通过。

直接核对原版 ELF 和私有诊断现场：`setEquipmentAniScriptLay` 查找 `equipment/character/atswordman.lay`，返回值等于该 map 的 end；该表当时有 10 项。原版代码未检查查找失败，随后在 `0x089c1eb4` 调用 snprintf 时使用无效模板字符串，glibc 的 strchrnul 读取低地址触发异常。不同运行的低地址值不同，不能把某一个错误指针当作固定缺陷地址。只读参考源码与这段原版指令语义一致。

这确认了此次崩溃的直接原因；模板为何缺失、是否存在完整的同版服务端 PVF 仍需继续核对。不能据此宣布所有 jbz69 数据不兼容，也不在 runtime 中伪造模板或跳过原版物品解析。原始资源未修改，自有进程均正常收回，私有诊断宿主已恢复为常规版本。脱敏记录见[客户端 PVF 启动证据](evidence/p8-client-pvf-startup.json)。
