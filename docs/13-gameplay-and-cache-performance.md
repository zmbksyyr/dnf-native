## 客户端实测

使用用户授权的 jbz69 客户端独立副本，客户端与服务端同时使用原服务包 PVF，SHA-256 为 `c3dde22a8b19e5deff5c498533e0830d13fec5605e81adeda9373841e6e22dec`。关闭客户端 `simplified_pvf` 后频道文字正常；原版认证实际成功，临时 RSA 公私钥匹配。

实际建立男鬼剑士，进入洛兰，完成移动、攻击、喝药、多房间转场、击杀 Boss、通关奖励及回城，客户端正常退出 0。等级从 1 升至 2，金币为 1060；冷重启后重新登录进入城镇，等级、金币、5 个复活币和装备可见。冷重启前后数据库十字段快照逐字节相同，覆盖等级、经验、金币、复活币及背包/装备完整字节的 SHA-256。截图、快照哈希及客户端返回码见[脱敏证据](evidence/p12-gameplay-and-cache.json)。

该次教程使用客户端 `full` 模式，带 GM、自动拾取等客户端功能；后续冷读使用 `fixonly`。本轮只认可上述操作、持久化和读回结果，不将评分、经验倍率、掉落或客户端插件语义计为纯净验收。早期这两次游戏验证后的整服关闭均超时并被夹具强制回收，不能计为正常停服通过。

当前定制 jbz69 PVF 仍缺 `equipment/character/atswordman.lay`；本次原包 PVF 对照不解决该缺口。客户端也仍会间歇出现登录前“图表系统建立失败”并退出 `0xc0000005`；最终性能修复后的这一轮复现了该错误，服务端尚未收到客户端认证，未完成修复后的真实玩家退出复验。

## 已定位的热点与最小修改

实际线程栈和 guest 寄存器显示：角色断开时，原版 `CUser::CacheCharacterMemory` 首次建立 `exchange_server::CCacheCharacterMgr` 的 1000 项池，每项 `0x3f864` 字节，总申请约 248 MiB。原包 JS 将物品 reset 替换成每次进入 JavaScript、分配 61 字节再复制的回调；缓存初始化反复进入该回调，产生密集系统调用与短命分配。此前只优化 runtime 内存检查后仍超过 180 秒，不能把它当作问题已经解决。

现在只替换原包已有的这一项 reset：61 字节清零直接由独立编写的 i386 SysV 指令完成，返回原指针并保留 EDI；不减少池容量，不删除物品字段。生成派生脚本前核对完整原脚本和 game 哈希，运行时核对 `0x080cb7d8` 的原始 22 字节。原始指令保存在内存，原脚本 dispose 时恢复；数据库关闭等原逻辑保留。磁盘 ELF 不变，Frida 关闭时不会应用此改动。新实例的资源构建记录保留来源、helper、派生脚本和补丁字节身份。

runtime 内存校验另在请求已完整覆盖时结束映射槽扫描，保留原有地址、权限和边界检查。未引入新的运行框架或依赖。

## 验证与范围

`python tools/test_frida.py --item-reset` 在真实原版 game/DP2/Lua/Frida 中通过：恰好清零 61 字节、两侧 sentinel 不变、返回指针正确、22 字节完全恢复、重复安装/恢复、原址 hook 和双向 Lua/JS RPC。原版 1000 项缓存构造为 94 毫秒，夹具按约定退出 42，无强制清理。

普通宿主和正式脚本的完整 16 服务自然启动为 35.517 秒，channel、relay、真实 monitor 拒绝与 STUN 协议通过，GUI/服务/数据库正常关闭，无强制回收。另一次在正式脚本末尾仅追加测试用定时调用，实际建立同一原版 1000 项缓存：构造 94 毫秒，完整栈启动 36.028 秒，请求关闭到最终 receipt 写入 26.870 秒，GUI 返回 0，无强制清理；测试后已恢复不含该定时调用的正式脚本。

两种完整运行和专项夹具均使用普通宿主。诊断宿主、INT80 改 UD2 的临时实验、第一版原生函数指针替换候选没有进入交付。双架构构建和 VM、TLS、跨进程信号专项对应当前 `runtime/run.c`；本轮未声称玩家负载 CPU 或内存降低的百分比，也未改变原版缓存池需要的内存。

首次创建回归的一次尝试中，资源、数据库、原种子往返和账号检查通过，但 relay 在开始协议检查前于 `0x0805b91a` 访问异常，导致 15 个 peer 存活断言失败。此地址为原版 `TManager<RelayService>::getManager()` 的读取；尚未定位传入对象异常的来源，保留失败现场，不能将复测通过解释为已经修复。

随后从最终 CAB 再次运行 `python tools/test_gui_setup.py --gui build/item-reset-resources/DNF-Native.exe`，两份新实例通过原始种子往返、18 库及当月表、每实例独立账号、原存储过程、15 个 peer 的协议、Frida 原数据库接口和正常关闭；GUI 退出 0，无强制回收，源资源未变。失败的存活断言已增加实际服务行信息，便于后续定位。

此前有一次 STUN 的 FS TLS 读取失败，后续独立诊断未复现，根因仍未定位；不将其写成已修复。安全三件套完整拓扑、大连接数、密码编辑、等级切换、core/full 分包和干净 Win7/Win11/断网验收仍待完成。
